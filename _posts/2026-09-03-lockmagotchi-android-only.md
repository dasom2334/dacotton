## Flutter가 맡은 것은 설정 화면뿐이었다

락마고치는 처음에 Flutter로 시작했다. 설정·상점·온보딩 같은 일반 앱 화면을 Android와 iOS가 함께 쓰게 하려는 생각이었고, iOS 시뮬레이터에서 실행도 확인했다.

그런데 락마고치의 중심은 잠금화면 배경(라이브 배경화면), 홈·잠금화면 위젯, 잠금 중에 여는 기기 제어 패널이다. 이 화면들은 운영체제가 정한 방식으로만 그릴 수 있고 Flutter를 돌리지 못한다. 첫 실험 단계에서 게임 로직은 Kotlin, Flutter는 화면만 맡기로 정한 순간 Flutter는 제품의 중심에서 빠져 있었다. 9월 3일 시점에 Flutter는 설정 화면 하나를 위해 Flutter 엔진, 네이티브와 주고받는 연결 코드, 그림을 문자열로 바꿔 넘기는 다리, 150MB짜리 디버그 앱을 남기고 있었다.

## iOS에서는 같은 제품을 만들 수 없었다

iOS에서 할 수 있는 것을 표로 정리해 보니, 잠금화면에서 움직이는 장면 자체가 없었다. iOS에는 앱이 배경화면을 바꾸는 기능이 없고, 잠금화면 위젯은 단색의 멈춘 그림이다. 그래서 공유할 본체가 없었다.

대안으로 iOS 축소판도 검토했다. 정지 이미지로 휴대폰을 꾸미고, 단색 위젯과 iOS 18의 제어 버튼 하나를 두는 형태다. 하지만 같은 이름을 단 다른 제품이 된다고 봤다.

## Android 전용으로 좁혔다

9월 3일 내가 정리한 판단은 "기기 의존도가 높아서 각 전용 앱으로만 만들어야 했다"였다. Flutter를 걷어 내고 Android 전용 Kotlin 앱으로 가기로 결정했다. iOS 앱은 만들지 않는다.

| 바뀌는 것 | 그대로인 것 |
| --- | --- |
| Flutter 화면, 연결 코드, 그림 전달 다리를 지운다 | 게임 규칙, 잠금화면 장면, 저장 로직 |
| 설정·온보딩을 Kotlin 화면으로 다시 만든다 | |
| Flutter 이름이 붙은 저장 파일·키를 정리한다 | |

같은 결정에서 잠금 중 조작 방법은 목표 기기인 삼성 갤럭시(One UI)에서 먼저 재 본 뒤 정하기로 했다. 픽셀 에뮬레이터에서만 확인한 [자체 패널](/log/2026/09/03/lockmagotchi-native-panel/)을 근거로 된다고 말한 것이 성급했기 때문이다.

## 결과

플랫폼을 하나로 좁혀, 잠금화면·위젯·패널을 그 운영체제의 기능에 맞춰 만드는 데 집중할 수 있게 됐다. 대신 iOS 사용자는 대상에서 빠졌다.

## 검증 범위

Kotlin으로의 전환은 로컬 작업 트리에서 진행했고 출시하지 않았다. One UI 측정은 이 결정 시점에 하지 않은 상태였다.
