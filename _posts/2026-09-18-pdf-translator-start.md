*3월 10일~4월 초 작업을 돌아본 기록이다. 글 날짜인 9월 18일이 구현일은 아니다.*

## 번역문을 원래 배치에서 읽고 싶었다

외국어 PDF의 문장을 따로 복사해 읽는 대신, 원래 문서의 자리에서 번역문을 읽고 싶었다. 텍스트와 페이지·좌표·폰트 정보를 추출하고 번역 뒤 같은 위치에 넣는 CLI로 범위를 잡았다. 내게는 AI 에이전트로 코딩하는 방식을 처음 익히던 시기의 프로젝트이기도 했다.

3월 10일 NestJS·TypeScript 골격에서 시작했지만 그대로 완성하지는 않았다. 3월 17~18일 구성을 다시 정리했고, 4월 초 추출·번역·생성·CLI 경로를 연결했다. 이 과정에서 번역 제공자를 바꾸는 일과 문서를 다시 그리는 일을 분리할 필요가 생겼다.

## 에이전트에게 넘길 구현 경계를 명시했다

작업을 나눠 맡기면 앞 세션의 설명이 다음 구현에 그대로 전달된다고 기대하기 어려웠다. 4월 2일에는 타입·열거형과 의존성 주입 계약을 명시하고, 각 단계가 어떤 입력을 받고 무엇을 반환하는지 맞췄다. 작성과 검수 역할도 분리했다. [당시 계약 정리 PR](https://github.com/dasom2334/pdf-translator/pull/19)은 이런 초기 개발 방식의 흔적이다.

문서를 늘리는 것만으로 해결되지는 않았다. 이후 PR에서는 오래된 기준 브랜치와 미완료 인계 때문에 통합 충돌과 재확인이 이어졌다. 계약 자체뿐 아니라 **어느 코드 버전에서 확인한 계약인지**를 함께 전달해야 했다. 이 실험이 개발 시간을 얼마나 줄였는지는 측정하지 않았다. 대신 독립된 작업을 합칠 때 확인할 경계가 드러났다.

## 제공자는 바꿔도 PDF 처리 흐름은 유지하도록

번역 제공자를 어댑터 뒤에 두고 추출한 위치 정보를 번역 이후까지 보존했다. MyMemory와 Gemini를 연결한 뒤 로컬 모델을 추가할 때도 문서 처리 쪽을 같은 인터페이스로 이어 가려는 선택이었다. 반면 제공자별 설정과 초기화 시점까지 공통 구조가 대신 해결하지는 못했다. 사용하지 않는 Gemini의 키를 요구하던 문제도 선택한 제공자를 실제 사용할 때 초기화하도록 고쳤다.

4월 초에는 파일이 끝까지 통과했지만, 그것이 읽기 좋은 번역문과 레이아웃을 보장하지는 않았다. 다음 문제는 원문을 어떻게 지우고 번역문을 넣을지, API 의존을 줄일 때 어떤 실행 부담을 가져올지였다.
