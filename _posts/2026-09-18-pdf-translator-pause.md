*4월 19~24일 로컬 모델 실험과 이후 남은 가독성 과제를 돌아본 기록이다.*

## API 비용 대신 로컬 자원을 감당하기로

제공자별 API 키와 호출 한도에 덜 의존하려고 로컬 모델을 어댑터로 연결했다. `node-llama-cpp`와 GGUF 모델을 사용했고, 기록으로 확인되는 실험에는 TranslateGemma 12B Q4_K_M이 있다. 모델을 받아 로컬에서 실행하면 호출별 API 비용은 피할 수 있지만, 장비 메모리·실행 시간과 번역 품질을 직접 감당해야 한다.

짧은 한국어 번역이 나오는 확인만으로 긴 PDF도 처리된다고 볼 수 없었다. 실제로 18페이지를 실행하자 메모리 문제와 강제 종료가 반복됐다. 당시 시도한 여러 모델 중 어느 것이 더 좋았다는 비교 점수는 남아 있지 않아 순위를 붙이지 않았다.

## 메모리를 비우려던 재생성이 부담을 만들었다

GPU 비율을 낮추고 컨텍스트 크기를 줄이거나 해제 뒤 1.5초·5초를 기다리는 수정으로도 긴 입력을 끝내지 못했다. 컨텍스트를 버리고 다시 만들 때 메모리 해제가 끝나기 전에 다음 큰 버퍼를 할당하는 경로가 문제로 좁혀졌다.

최종 수정은 컨텍스트를 유지한 채 블록마다 `sequence.clearHistory()`로 KV 캐시를 비우는 방식이었다. 채팅 래퍼 대신 completion 경로를 쓰고 출력 토큰도 제한했다. [PR #60의 최종 실행 기록](https://github.com/dasom2334/pdf-translator/pull/60#issuecomment-4304277531)에는 16GB Apple Silicon Mac에서 18페이지·422블록을 처리해 약 6.4GB 메모리로 완료했다고 남아 있다. 앞선 실패를 포함한 한 문서의 검증이며, 모든 PDF·모델에서 메모리 문제가 해결됐다는 수치는 아니다.

## 실행 완료와 읽고 싶은 번역은 별개였다

로컬 어댑터 PR은 머지됐고 PDF를 받아 번역 PDF를 만드는 1차 경로는 갖췄다. 그러나 번역 품질과 출력 가독성은 충분하지 않았다. 긴 번역문을 작은 글씨나 말줄임으로 맞추는 것으로는 읽기 좋은 문서가 되지 않는다. 8월의 원문 제거 후속 역시 이 간격을 줄이려는 미완료 작업이다.

현재는 1차 완성 뒤 중단한 상태다. 다시 읽고 싶은 외국어 PDF가 생기거나, 가독성을 개선할 좋은 방법이 떠오르면 재개할 생각이다. 다음 검증에서는 완료 여부와 메모리뿐 아니라 실제 문장을 빠짐없이 자연스러운 순서로 읽을 수 있는지를 봐야 한다.
