## 로그에 200이 줄지어 있었다

9월 16일 냠의 운영 로그에서 설정 파일·인증 키·PHP 진단 파일처럼 흔히 노리는 이름의 주소를 차례로 찔러 보는 자동 요청을 발견했다. 이런 요청은 공개된 사이트라면 흔히 받는다. 문제는 이 요청들이 모두 200(정상 응답)을 받고 있었다는 점이다.

## 응답 본문은 홈페이지였다

확인해 보니 응답 본문은 홈페이지 HTML과 똑같았다. 냠의 웹 화면은 HTML 한 장이 주소에 따라 다른 화면을 그리는 방식(SPA)이다. 그래서 서버는 모르는 주소가 와도 일단 홈페이지를 돌려주게 돼 있었다. 실제 파일이 노출된 것은 아니었지만, 로그만 보면 "그 파일이 있다"는 응답처럼 보였고, 진짜 문제가 생겼을 때 로그로 구분하기도 어려웠다.

## 화면 주소만 홈페이지로

서버를 고쳐, 실제로 있는 화면 주소에만 홈페이지를 돌려주고 탐색에 쓰이는 숨김 파일·PHP·SQL 같은 주소에는 404를 돌려주게 했다(커밋 6220957, 9/16 14:30 KST). 새 화면을 만들면 화면 주소 목록에도 등록해야 하는 규칙이 생겼다. 서버 테스트에 탐색 주소 19개를 넣었고, 기존 서버에서는 이 테스트가 실패하는 것을 먼저 확인했다.

수정은 이틀 동안 배포되지 않았다. GitHub에 올리는 과정에서 자동 검토가 외부 전송 승인이 분명하지 않다며 막았고, 내가 적용과 배포를 승인한 뒤 PR #63으로 9월 18일 21:34 KST에 병합되고 자동 배포됐다.

## 결과

배포 뒤 운영에서 탐색 주소는 404, 정상 화면·서버 상태 확인·제품 API는 200을 받는 것을 확인했다. 이제 로그의 200은 실제로 있는 화면에 대한 응답이다.

## 검증 범위

이 요청으로 실제 파일이 유출된 사실은 없다. 404 처리는 응답을 정확하게 만든 변경이고, 이것으로 공격이 막히지는 않는다. 자동 요청이 냠의 주소를 어떻게 알았는지는 확인하지 못했다.
