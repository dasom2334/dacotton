## 화면 셋, 실행 주체 셋

앱 밖에서 캐릭터를 보여 주려면 Android의 서로 다른 세 화면을 써야 했다.

| 화면 | 누가 그리나 | 상태를 바꾸는 방법 |
| --- | --- | --- |
| 일반 앱 | Flutter(Dart) 코드 | 앱 안의 버튼 |
| 홈 위젯 | 홈 런처가 앱이 넘긴 `RemoteViews`(뷰 설명서)를 대신 그린다 | 버튼을 누르면 앱의 Kotlin 수신기로 브로드캐스트가 간다 |
| 라이브 배경화면 | Kotlin `WallpaperService`가 캔버스에 직접 그린다 | 직접 조작은 없고, 저장된 값을 읽어 그린다 |

셋은 서로의 메모리를 볼 수 없다. 앱에서 밥을 줘도 위젯과 배경화면이 그 값을 모르면 화면마다 다른 다마고치가 된다. 그래서 8월 29일 첫 실험은 캐릭터 그림 없이 배고픔 값 하나와 밥주기 버튼 하나로, 세 화면이 같은 상태를 이어 쓰는지만 확인했다.

## 같은 파일을 읽게 했다

Flutter 쪽 저장은 `shared_preferences` 패키지를 썼다. 이 패키지의 레거시 API는 Android 기본 저장소인 SharedPreferences의 `FlutterSharedPreferences` 파일에 `flutter.` 접두어를 붙여 값을 쓴다. Kotlin 쪽에 같은 파일과 키(`flutter.hunger`)를 읽고 쓰는 작은 저장 객체를 두면, 다리 코드 없이 두 언어가 같은 값을 본다. 패키지의 새 Async API는 저장소가 DataStore로 바뀌어 이 파일 공유가 되지 않으므로 레거시 API를 유지했다.

에뮬레이터(Pixel 7 프로필, API 36)에서 두 가지를 확인했다. 앱을 재시작해도 값이 남는지, Kotlin에서 값을 바꾸면 앱이 그 값을 읽는지다.

## 저장과 갱신 알림은 별개였다

홈 위젯에는 배고픔 값과 밥주기 버튼을 올렸다. 위젯의 버튼을 누르면 Kotlin 수신기가 파일의 값을 올리고 위젯을 다시 그리게 한다. 앱이나 잠금 해제 화면이 열리지 않고 값이 바뀌었다. 반대로 위젯에서 바꾼 값이 앱에 보이도록, 앱이 다시 앞으로 올 때 값을 새로 읽게 했다.

남은 구멍은 반대 방향이었다. 앱에서 밥을 주면 Dart가 파일에 직접 쓰는데, 위젯은 그 사실을 모르니 예전 숫자를 계속 보여 줬다. 홈 런처는 앱이 "다시 그려라"라고 알리기 전까지 위젯을 갱신하지 않는다. 그래서 앱이 밥을 준 뒤 Flutter와 Kotlin 사이의 통로(MethodChannel)로 `refreshWidget`을 불러 위젯을 다시 그리게 했다. 같은 파일을 읽는 것으로 값은 공유됐지만, 화면이 그 값을 다시 읽게 하는 신호는 화면마다 따로 필요했다.

## 배경화면도 같은 값을 그렸다

이어서 Kotlin 캔버스로 600ms마다 두 프레임을 번갈아 그리는 라이브 배경화면을 만들었다. 프레임마다 저장된 값을 읽으므로, 위젯에서 밥을 주면 다음 프레임에 배경화면에도 반영됐다. 화면을 껐다 켜도 잔상이 남지 않았고, 배경화면 선택기에서 홈과 잠금화면 모두에 적용하는 선택지가 나왔다. 이 정도 장면에는 별도 게임 렌더링 엔진이 필요 없었다.

세 화면이 하나의 상태로 이어진 뒤에야 그림 방향을 골랐다. 레트로 픽셀로 정하고, 제품 화면에서는 숫자 대신 클래식 다마고치처럼 하트·표정·똥으로 상태를 보여 주기로 했다. 실험에서 쓴 숫자는 값이 바뀌는지 확인하는 용도로만 남겼다.

## 남은 것은 잠긴 화면에서 누르는 일

홈 위젯에서 앱을 열지 않고 돌볼 수 있다는 것은 확인했다. 하지만 잠금화면은 운영체제가 입력을 따로 다루므로, 홈에서 된다고 잠금 중에도 된다고 볼 수 없었다. 다음 실험은 잠금 상태에서 돌보기 버튼을 누를 수 있는 경로를 하나씩 확인하는 일이었다.

## 검증 범위

여러 프로세스가 같은 파일에 동시에 쓸 때의 정합성은 이 실험에서 확인하지 않았다. 결과는 에뮬레이터 기준이며 삼성 기기에서는 별도로 보지 않았다.
