## 테스트가 통과해도 묻지 않은 질문은 남는다

조건을 고르면 목록이 나오고 제품 상세에서 근거를 볼 수 있었다. 9월 9~10일 평가 시점에는 서버 테스트 139개, 웹 테스트 5개와 빌드도 통과했다. 그런데 이 결과만으로 보호자가 받는 설명이 맞는지까지 확인한 것은 아니었다.

그래서 조건 고르기 → 목록 → 제품 상세 근거로 이어지는 화면을 다시 따라가는 것과 함께, 결과가 달라져야 하는 작은 입력을 따로 만들었다. 실제 수집 자료로 DB를 재구성해 표본을 살피고, 숫자와 레시피를 통제한 반례로 경계가 유지되는지 확인했다.

## 숫자·시간·출처에서 서로 다른 문제가 나왔다

보장성분표의 수치는 `(min) 8%`, `(max) 85%`처럼 최소나 최대 한쪽만 적힌 경우가 많다. 그런데 이 값을 꺼내는 과정에서 최소·최대 구분이 빠지고 숫자 8만 남아, ‘최소 8%’인 제품이 ‘8% 이하’ 조건을 통과했다. 실제로는 9%일 수도 20%일 수도 있는 제품이다. 또 3월에 먹인 제품의 9월 레시피를 바꾸자 과거 기록에서 계산한 후보가 사라졌다. 급여 기록은 보존됐지만 그 해석은 최신 상품 정보에 묶여 있었다.

출처 설명에도 별도 문제가 있었다. 웹과 OCR의 내용이 다른데 최종 포함 판정이 같다는 이유로 대조가 완료된 것처럼 표시할 수 있었다. 제품 조건의 결과와 두 자료의 일치 여부는 서로 다른 질문인데 하나의 신호로 표현한 탓이었다.

## 문제별로 보존해야 할 의미를 정했다

숫자는 `(min) 8%`를 (8, 없음), `(max) 85%`를 (없음, 85), 구분 없는 확정값을 (v, v)의 범위로 바꿔 판정과 건물·열량 기준 환산까지 유지했다. 상한 조건은 표기에 상한이 있을 때만 통과하고, 범위가 경계에 걸치면 이유와 함께 확인 불가로 둔다. 급여 기록에는 레시피 근거를 남기고, 출처 상태는 웹 표기와 사진 표기를 원료 분류(닭·연어처럼 여러 표기를 묶은 공통 원료 이름) 단위로 따로 견줘 일치·부분 일치·차이로 표시하고, 판정 결과와 별도로 보여 주게 했다. 조건이 없을 때도 통과라고 부르지 않고 ‘대조하지 않음’으로 구분했다.

수정 뒤 같은 반례를 다시 실행했다. 최소값의 상한 조건은 확인 불가로, 서로 다른 출처는 차이 있음으로 바뀌었고, 새 레시피를 넣어도 과거 급여의 후보가 유지됐다. 이 검증은 함수 하나보다 DB의 사전·이력에서 API까지 의미가 이어지는지를 보는 쪽에 가까웠다.

## 수정 완료와 사용 효과는 따로 확인한다

9월 10일 수정 후 서버 테스트는 162개, 웹 테스트는 11개가 됐고 실제 PostgreSQL과 브라우저에서도 조건 선택·목록·상세 화면을 확인했다.
