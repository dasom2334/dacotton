## 로그가 있어도 실패 이유는 안 보였다

배포 뒤 Cloud Logging을 살폈을 때 평문 로그는 오류와 경고까지 INFO로 모였다. 로그 줄이 존재해도 어느 것이 실패인지 바로 고르기 어려웠다. 소셜 로그인 실패도 리다이렉트 상태만 남아, 왜 돌아왔는지 알기 어려운 경우가 있었다.

9월 13일에는 JSON 로그에 severity와 사건 정보를 담게 했다. 로그인 상태값 검증도 세션에 값이 없는 경우와 값이 다른 경우를 나눠 기록했다. 사용자가 받는 오류 화면을 늘리는 대신 운영자가 실패 단계를 되짚을 정보를 남긴 것이다.

## 어떤 조작이 얼마나 걸렸는지

API 접근 로그에는 경로·응답 상태·처리 시간·요청 조건을 남겼다. ‘검색이 안 됐다’는 말을 받으면 요청이 서버까지 왔는지, 거절됐는지, 느리게 끝났는지 구분하려는 목적이다. Cloud Run의 기본 요청 로그에 앱에서만 아는 정보를 보탰다.

요청 본문은 읽어 로그에 남기지 않고, 쿼리의 토큰·인가 코드 등은 가리며 사용자는 내부 ID로만 식별했다. 자세히 기록하는 것과 모든 입력을 저장하는 것은 달랐다. 분석에 필요한 값과 남기면 안 될 값을 함께 정했다.

## 웹 상태와 데이터 상태는 따로 점검한다

프로세스가 응답하는 health 경로는 서비스가 살아 있는지 확인하는 출발점이다. 제품 표기가 온전히 남았는지, 사용자 기록이 저장되는지까지 확인해 주지는 않는다. 그래서 9월 15일에는 운영 데이터를 읽기만 하는 점검 명령과 수동 GitHub Actions 경로도 마련했다. 브랜드별 제품과 누락된 사진·보장성분 등을 따로 볼 수 있게 했다.

Mac의 수집·백업 작업에는 실행 로그와 마지막 성공 시각을 남겼다. 상태 명령으로 성공 기록이 없는 작업과 오래된 성공 기록을 구분한다. 이것 역시 확인할 수 있는 도구이지, 실행하지 않아도 모든 장애를 통보하는 장치와는 다르다.

| 확인할 질문 | 남긴 신호 | 이것만으로 알 수 없는 것 |
| --- | --- | --- |
| 요청이 어디서 실패했나 | 상태·처리 시간·인증 실패 단계 | 제품 데이터의 완전성 |
| 예약 작업이 실제 끝났나 | 실행 로그·마지막 성공 시각 | 추출한 내용의 정확성 |
| 갱신하며 근거를 잃었나 | 브랜드·제품별 누락 점검 | 모든 원문의 의미적 정확성 |

## 아직 자동 경보까지 갖춘 상태는 아니다

9월 21일 실제 프로젝트 조회에서 Cloud Monitoring 알림 정책과 uptime check는 빈 목록이었다. 따라서 현재 운영을 상시 장애 알림이 완성된 체계라고 쓰지 않는다. 구조화 로그와 수동 점검 경로로 운영을 살피는 단계다.

첫 배포에서는 예산 경보도 설정했지만, 당시 기록에는 크레딧이 비용을 상쇄해 경보 판단에 영향을 주는 문제가 남아 있다. 오늘의 예산 알림 전달까지 재검증한 것은 아니다. 또한 DB를 매분 읽는 확인은 휴면을 깨워 무료 사용량에 영향을 줄 수 있어, 프로세스 확인과 실제 데이터 검증을 같은 빈도로 돌리는 방식은 택하지 않았다.

## 관찰할 수 있게 만든 뒤 실제 문제를 찾았다

이후 로그에서 자동 탐색 경로를 발견했고, 예약 작업 기록에서는 카탈로그 갱신 실패를 확인했다. 데이터 내용까지 대조하자 최신 수집일과 정상 응답 뒤에 보장성분 누락도 남아 있었다. 각각 다른 신호로 발견한 문제이므로 ‘서버가 켜져 있다’ 한 가지로 운영을 닫을 수 없었다.
