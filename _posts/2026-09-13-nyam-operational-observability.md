## 로그 줄보다 실패 단계를 남겼다

첫 배포 뒤에는 오류와 경고까지 INFO로 모여 실패를 구분하기 어려웠다. 9월 13일 JSON 로그에 severity와 사건 정보를 넣고, 로그인 상태값이 없는 경우와 다른 경우를 나눴다. API에는 경로·상태·처리 시간·요청 조건을 남겨 요청이 도착하지 않은 것인지, 거절된 것인지, 느린 것인지 따라갈 수 있게 했다.

요청 본문은 기록하지 않고 쿼리의 토큰·인가 코드는 가렸다. 분석에 필요한 정보를 늘리는 일과 사용자의 입력을 전부 저장하는 일을 구분했다.

## 요청·예약 작업·데이터는 다른 신호가 필요했다

| 확인할 질문 | 남긴 신호 | 이것만으로 알 수 없는 것 |
| --- | --- | --- |
| 요청이 어디서 실패했나 | 상태·처리 시간·인증 실패 단계 | 제품 데이터의 완전성 |
| 예약 작업이 실제 끝났나 | 실행 로그·마지막 성공 시각 | 추출한 내용의 정확성 |
| 갱신하며 근거를 잃었나 | 브랜드·제품별 누락 점검 | 모든 원문의 의미적 정확성 |

9월 15일에는 운영 데이터를 읽기만 하는 점검 명령과 수동 GitHub Actions 경로도 마련했다. 프로세스가 살아 있다는 health 응답만으로 보장성분이나 사진 누락까지 발견할 수는 없기 때문이다. Mac 수집·백업 역시 예약 설치 여부와 마지막 성공 시각을 별도로 봤다.

## 자동 경보가 완성된 운영은 아니었다

9월 21일 조회에서는 Cloud Monitoring 알림 정책과 uptime check가 없었다. 당시 기반은 구조화 로그와 수동 점검이었다. 예산 경보에도 크레딧 상쇄가 판단에 영향을 주는 문제가 남았다. DB를 자주 읽는 점검은 휴면을 깨울 수 있어 프로세스 확인과 데이터 검증을 같은 빈도로 돌리지 않았다.

이후 실제 발견과 조치는 [예약 갱신 복구](/log/2026/09/20/nyam-refresh-recovery/)와 [정상 응답 뒤의 데이터 누락](/log/2026/09/20/nyam-data-quality-monitoring/)에서 이어진다. 관측 수단을 마련한 것과 장애를 항상 자동으로 발견하는 것은 구분한다.
