## 베타에서 먼저 줄일 비용을 골랐다

최대 200명 정도를 대상으로 사용 가치와 수익 가능성을 확인하려는 단계였다. 외부 로드밸런서와 별도 엣지 방어의 고정비는 미루고, 앱의 반복 계산과 단순 과사용을 줄이는 쪽을 택했다. 이 판단은 예상 참여 규모에 맞춘 비용 선택이며 공격이 없으리라는 보장은 아니었다.

## 캐시와 요청 제한이 맡은 범위

9월 11일에는 제품 원문 해석을 공개 시점에 저장했고, 13일에는 같은 조건의 목록 응답을 프로세스 메모리에 60초 보관했다. 조건이 달라지면 다시 계산하고, 관리자 수정이 목록에 보이기까지 최대 1분 늦어질 수 있다. 계산 시점을 바꾼 뒤 응답 재사용을 더한 것이므로, 앞서 제거한 조건별 2분 캐시와는 단계가 다르다.

| 선택 | 줄이는 비용 | 남는 제약 |
| --- | --- | --- |
| 저장된 제품 해석 재사용 | 요청마다 원문·사전을 다시 읽는 비용 | 사전 변경 시 관측을 갱신해야 함 |
| 짧은 응답 캐시 | 같은 조건의 반복 조회 | 서로 다른 조건은 캐시를 우회하고 갱신 지연이 생김 |
| 앱 요청 제한 | 단순 반복 조회·등록의 과사용 | 프로세스별 집계, 재시작, 동시 요청에 한계 |
| 인스턴스 확대 제한 | 급격한 자원 확대 | 요청이 몰리면 대기·실패 가능 |

## 앱이 싸게 처리하는 것과 공격을 막는 것은 다르다

제한 카운터는 프로세스 메모리에 있어 여러 프로세스가 전역 횟수를 정확히 공유하지 않는다. 여러 출발지의 요청도 앱 제한만으로 막을 수 없다. DRF 역시 앱 수준 제한을 DoS 방어로 설명하지 않는다. [DRF Throttling 문서](https://www.django-rest-framework.org/api-guide/throttling/)

앞단 정책을 도입한다면 앱의 직접 주소로 우회하지 못하게 하는 구성까지 필요하다. 로드밸런서 하나를 추가하는 것으로 방어가 끝나지는 않는다. [Cloud Armor 연동 문서](https://docs.cloud.google.com/armor/docs/integrating-cloud-armor)

## 감수한 위험을 다시 볼 신호

당시에는 작은 베타를 표적으로 삼을 유인이 낮다고 판단했지만, 이후 로그에는 자동 탐색 요청이 실제로 나타났다. 의도적인 표적 공격이 드물 것이라는 예상만으로 운영 위험을 없앨 수는 없었다.

9월 21일 조회에서는 현재 리비전의 최대 인스턴스가 1이었다. 이 선택은 가용성과 맞바꾸는 비용 제어였고 고정 청구액 상한이나 동시 이용자 수의 성능 보장은 아니었다. 요청·오류·비용을 보며 재검토해야 한다. [Cloud Run 최대 인스턴스 문서](https://docs.cloud.google.com/run/docs/configuring/max-instances)

당시 운영은 구조화 로그와 수동 점검 단계였다. 제한과 캐시를 적용했다는 사실보다, 실제 이용이 지연·오류로 막히거나 자동화 요청이 부하를 만든다면 앞단 방어와 가동 비용을 다시 비교해야 한다는 조건을 남겼다.
