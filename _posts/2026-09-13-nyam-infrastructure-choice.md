## 서버보다 먼저 정한 실험의 크기

냠은 처음부터 큰 서비스의 인프라를 갖추려는 프로젝트가 아니었다. 친구가 실제로 필요한 기능을 만들고, 고양이 커뮤니티에서 많으면 200명 정도에게 베타를 써 보게 하면서 쓸모와 쿠팡 파트너스 수익 가능성을 확인할 요량이었다. 아직 수익이 확인되지 않은 단계이므로 매달 먼저 나가는 비용을 작게 유지하고 싶었다.

이 200명은 예상 참여 대상의 상한이다. 이미 확보한 사용자 수나 동시에 접속해도 된다는 부하 시험 결과가 아니다. 200명이라는 구체적 규모는 기존 인프라 문서에서 찾지 못해 이후 직접 설명한 계획으로 구분했고, 인프라 결정과 배포는 9월 12~13일 기록을 기준으로 정리했다.

## 비교와 세팅을 함께 진행했다

처음에는 Render와 Neon, Koyeb을 검토했다. 이후 작은 GCE VM에 앱과 PostgreSQL을 함께 넣는 안은 배포 파이프라인과 복원 검증까지 준비했다. 표에서 하나를 고른 뒤 처음부터 끝까지 구현한 것이 아니라, 선택을 비교하면서 실제 세팅도 진행했다.

그러다 비용과 함께 데이터 보존이 중요한 기준이 됐다. 수집 제품은 다시 모을 여지가 있지만 친구가 남긴 급여 기록은 그렇지 않다. VM 하나에 앱과 DB를 모으면 단순하고 저렴한 대신, 장애가 둘을 함께 멈추게 하고 OS 패치·DB 운영도 직접 맡아야 한다. 만들어 둔 코드가 있다는 이유만으로 이 부담을 고정하고 싶지는 않았다.

| 대안 | 얻는 것 | 받아들여야 할 비용·부담 | 당시 판단 |
|---|---|---|---|
| 작은 VM + 자체 PostgreSQL | 작은 고정비, 직접 통제 | 앱·DB 장애가 겹치고 패치·복구를 직접 운영 | 파이프라인까지 준비했지만 운영 경로로는 보류 |
| Cloud Run + Cloud SQL | 앱과 관리형 DB 조합, 백업 운영 부담 감소 | 유휴에도 DB 고정비가 남음 | 수익 검증 전 베타에서 먼저 지불하지 않기로 함 |
| Cloud Run + Neon Free | 앱·DB가 유휴에 쉬고 낮은 비용으로 시작 | 첫 요청 지연, 무료 사용량 제약, 별도 백업 관리 | 베타를 시작할 조합으로 선택 |
| AWS의 관리형 DB 조합 | 다른 관리형 운영 선택지 | 당시 비교한 최소 DB 비용과 무료 제공 기간 조건 | 이번 소규모 베타의 우선안으로 고르지 않음 |

표는 당시 비교한 판단이다. 현재 가격표나 모든 서비스의 우열을 뜻하지 않는다.

## 콜드스타트는 없애지 않고 감수했다

Cloud Run은 최소 인스턴스를 0으로 두고 Neon은 무료 플랜에서 시작했다. 접속이 뜸하면 DB가 쉬었다가 다음 요청에 깨어나는 지연을 감수하는 대신, 수익을 확인하기 전부터 상시 가동비를 만들지 않으려 했다. Neon의 무료 플랜은 비활성 5분 뒤 compute가 휴면하는 구조다. [Neon 공식 설명](https://neon.com/blog/why-you-want-a-database-that-scales-to-zero)

첫 배포 기록의 2~4초는 앱 기동과 DB 깨우기가 함께 걸린 당시 지연이다. Neon만의 고정 응답 시간이나 현재 보장값이 아니다. Cloud Run의 최소 인스턴스를 1로 올려도 Neon의 휴면까지 자동으로 없어지지는 않는다. 지연을 줄이려면 앱과 DB를 각각 보고 추가 비용을 판단해야 한다.

국내 사용자와 미국 리전 사이의 거리도 받아들였다. 앱만 서울로 옮기면 DB와의 왕복이 남으므로 둘의 위치를 함께 바꿔야 했다. 베타에서 기다림이 실제 사용을 막는지 먼저 보고, 그때 가동 방식과 리전을 다시 비교하기로 한 선택이었다.

## 200명이라고 무료가 보장되지는 않는다

무료 한도는 회원 수보다 요청 횟수·DB 전송량·깨어 있는 시간에 영향을 받는다. 200명이 드문드문 쓰는 것과 매일 여러 번 쓰는 것은 다르다. 당시 추정표도 방문당 요청 횟수에 기대고 있었으므로, 참여 대상 수를 그대로 무료 수용 인원으로 바꿀 수는 없다.

예를 들어 200명이 한 달 30일 동안 하루 한 번만 방문해도 6,000방문이다. 같은 조건을 반복 조회해 캐시를 쓰는 비율과 실제 사용 시간을 더 봐야 한다. 목표는 ‘200명을 무료로 감당했다’가 아니라, 그 규모까지 베타를 열어 보며 비용과 수익 가능성을 함께 확인하는 것이었다.

## 관리형 DB를 골라도 복원 책임은 남는다

Neon을 선택하면서 Mac의 예약 덤프와 빈 DB 복원 확인을 함께 준비했다. 관리형 서비스의 복구 기능에만 기대지 않고, 서비스 밖에 데이터를 꺼내 다시 넣을 수 있어야 선택을 바꿀 수 있기 때문이다. 백업이 필요한 때에는 Mac과 Docker가 실제로 실행돼 있어야 하는 부담도 받아들였다.

PostgreSQL과 덤프·복원 경로는 다른 환경으로 옮길 때의 선택지를 남겼다. 이식이 공짜라는 뜻은 아니다. 데이터뿐 아니라 비밀 설정·연결·지연과 실제 복원 결과까지 다시 확인해야 한다. 낮은 비용으로 시작하되, 무료 한도나 대기 시간이 베타의 사용을 막으면 옮길 수 있게 하는 것이 이 결정의 근거였다.

## 운영하면서 다시 보게 된 비용 가정

9월 28일에는 브랜드 확대 중 무료 DB 전송 한도에 막혔다. 초기 비용 예상은 방문당 요청에 기대고 있었지만, 운영자가 반복하는 백업·재처리·검증도 전송을 만든다. 각 작업의 기여량을 분리하지는 못했으므로 한도 소진을 특정 작업 하나의 탓으로 확정하지 않았다.

이후에는 로컬에서 검증한 변경분을 운영에 보내고, 그 제품 키만 다시 확인하는 경로를 만들었다. 무료 인프라 선택을 유지할지와 별개로 운영 작업의 범위도 비용 모델에 들어가야 했다.
