## 주소가 열린 뒤에도 배포는 반복된다

9월 13일 냠을 실제 도메인에 배포했다. 처음에는 DB와 가까운 도시의 Cloud Run 리전을 골랐지만 원하는 도메인 매핑을 지원하지 않아 북버지니아로 옮겼다. 같은 이미지 다이제스트를 지정해 다시 배포했고, 도메인과 인증서가 연결되는 것을 확인했다.

지역을 고르는 기준도 단순한 거리만으로 끝나지 않았다. 필요한 배포 기능을 쓸 수 있는지까지 포함해야 했다. 그리고 한 번 주소가 열린 다음에는 새 코드를 어떻게 넣고 실패하면 무엇을 유지할지 정해야 했다.

## 검증한 이미지에만 트래픽을 보낸다

자동 배포는 테스트한 커밋의 이미지로 마이그레이션을 수행하고, 새 리비전(Cloud Run에 올라간 배포 버전 하나)에 바로 트래픽을 주지 않는 순서로 만들었다. 새 버전 전용 주소에서 스모크 테스트(주요 화면과 API가 응답하는지 보는 짧은 확인)를 통과한 뒤에만 전환한다. 후보가 실패하면 기존 리비전이 계속 응답하도록 했다.

마이그레이션은 트래픽 전환 전에 돌기 때문에, 후보가 실패해도 DB 변경까지 되돌아가지는 않는다. 그래서 배포가 겹쳐 마이그레이션이 충돌하지 않게 직렬화하고, 런타임 DB 계정과 스키마를 변경하는 계정도 나눴다. 평소 요청을 처리하는 앱에 배포 작업의 권한까지 줄 필요가 없었기 때문이다.

## 백업은 실제로 복원해 확인했다

제품 목록은 다시 모을 수 있어도 사용자 기록까지 같은 방식으로 재생할 수는 없다. 그래서 백업은 파일이 생성되는지 확인하는 데서 멈추지 않았다. 덤프를 빈 PostgreSQL 컨테이너에 복원한 뒤 모든 테이블의 행 수를 운영과 대조했다.

그때 측정한 백업은 6분 33초, 복원은 1.2초였고 덤프 크기는 994KB였다.

## 설치한 예약과 확인한 알림을 구분

주간 수집 예약도 설치했고 테스트 푸시가 실제 브라우저에 도착하는 것을 확인했다. 하지만 테스트 메시지를 보낸 것과 제조사 자료가 바뀌어 알림이 생성되는 것은 다른 과정이다. 실제 두 번의 수집 이력이 비교되는지까지 확인해야 했다.

첫 배포로 공개 주소와 함께, 다시 배포하는 절차와 백업을 되살리는 절차를 마련했다. 그다음부터는 이 작업들이 실제로 계속 끝나는지 보는 운영이 시작된다. 뒤의 갱신 점검에서는 예약을 설치했다는 사실만으로 닫을 수 없었던 문제가 드러났다.

## 검증 범위

복원 시험은 그 시점 데이터 한 번의 확인이며, 매일 예약 백업이 계속 성공하는지는 별도로 봐야 한다. 수집 예약과 테스트 푸시는 설치·도착까지 확인했고, 실제 레시피 변경으로 알림이 생성되는 경로는 이때 확인하지 않았다.
