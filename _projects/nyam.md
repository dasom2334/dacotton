## 친구의 사료 목록에서 시작했다

친구는 당뇨가 있는 고양이를 돌보며 엑셀에 사료 목록을 관리했다. 제품별 알레르기 관련 성분, 인 같은 영양 수치, 탄수화물 비율과 개인 메모를 기록하고, 공개되지 않은 정보는 제조사에 직접 이메일로 문의해 받았다.

나는 그 반복 작업을 줄이고 싶어 냠을 만들었다. 제조사의 공개 정보를 모아 원료와 영양 수치 조건으로 제품을 찾고, 먹인 제품과 원료별 상태를 남기는 서비스다. 단백질과 인 같은 상세 성분 정보도 친구가 고양이에게 먹일 제품을 고를 때 자신이 피하려는 조건에 해당하는지 확인할 수 있도록 추가했다.

## 원문을 남기고 각자의 조건으로 찾는다

냠은 제조사가 적은 원문, 프로그램이 해석한 정보, 사용자 조건에 따른 결과를 구분한다. 원문의 ‘chicken’을 ‘닭’으로 연결하는 해석은 공유할 수 있지만, 닭을 피할지는 사용자가 정할 조건이다. 수집 프로그램이 원문을 가져오면 서버가 해석을 제품 이력별로 저장하고, 검색할 때 그 결과에 사용자 조건을 대조한다. 같은 자료를 거듭 해석하는 대신 원문이나 사전이 바뀔 때 저장된 해석을 갱신해야 한다.

조건에 걸리지 않았다는 결과와 자료가 부족해 판단하지 못했다는 결과도 나눈다. 제품에 ‘단백질 최소 8%’라고 적혀 있을 때, 사용자가 ‘8% 이하’를 찾는다면 실제 함량은 더 높을 수 있으므로 확인이 필요하다. 냠은 조건 대조의 결과와 그 이유를 보여주며, 제품 자체의 안전성을 확정하지 않는다.

친구가 요청한 비교 화면에서는 최대 네 제품의 원재료와 영양 수치를 나란히 본다. 수분을 뺀 기준으로 비교하고, 탄수화물은 다른 영양 수치에서 계산한 추정값임을 표시한다. 비교용 대표값으로 실제 함량을 확정하지 않으며, 검색에는 최소·최대 범위를 유지한다. 필요한 정보가 빠지면 0으로 채우지 않고 이유를 남긴다.

## 엑셀과 함께 쓰며 확인하는 것

친구는 지금도 냠과 엑셀을 함께 사용한다. 제조사에 개인적으로 받은 비공개 정보와 메모는 엑셀에 남겨야 하기 때문이다. 그러면서 냠에서 이전에는 몰랐던, 자신이 정한 회피 조건에 걸리지 않는 제품을 발견해 좋아했다.

내가 확인한 효용은 그 새로운 선택지였다. 모든 자료를 옮기거나 절약한 시간을 측정한 것은 아니다. 서비스를 운영하며 상품 비교, 브랜드 추가와 빠진 성분 정보 같은 피드백을 반영하고, 보호자에게 얼마나 도움이 되는지와 수익 가능성을 확인해 나가고 있다.

## 기술 구성

| 맡은 일 | 사용 기술 |
| --- | --- |
| 제품 검색·비교 화면 | React 19와 TypeScript로 화면을 만들고 Vite로 빌드한다. 화면 코드 검사는 Vitest를 사용한다. |
| 제품·조건 조회 API | Python의 Django 5.2와 Django REST Framework가 요청을 처리한다. |
| 제품 원문·해석 결과 저장 | Neon의 PostgreSQL을 사용하며, 서버는 psycopg로 연결한다. |
| 제조사 웹자료 수집 | Python 수집 코드에서 curl_cffi로 웹 요청을 보낸다. |
| 서버 실행과 정적 파일 제공 | Gunicorn이 Django를 실행하고 WhiteNoise가 정적 파일을 제공한다. |
| 빌드·배포 | Docker로 화면과 서버를 하나의 이미지에 담고, GitHub Actions에서 Artifact Registry를 거쳐 Google Cloud Run으로 배포한다. |

Docker 빌드에서는 Node 22로 웹 화면을 빌드한 뒤, 그 결과물과 서버 코드를 Python 3.12 이미지에 함께 넣는다.
