## 푸시는 있었지만 배포는 없었다

새 main 커밋은 `49ed47f`, 라이브는 `b60d6f9`였다. GitHub CI는 머지 3초 뒤 실행됐고, Vercel의 프로덕션 브랜치와 일시 중지 여부, 빌드를 건너뛰는 설정도 확인했다. 그런데 조사할 새 배포 자체가 없었다.

## 실패 여부보다 실행의 존재부터

체크가 실패했는지를 보는 방식은 체크가 붙지 않는 상황을 지나칠 수 있다. 이 경우에는 ‘새 커밋에 대응하는 프로덕션 배포가 생겼는가’가 먼저였다.

## 관측 결과별 처리

| 관측 | 처리 방향 |
|---|---|
| 해당 커밋의 배포 확인 | 정상 완료로 판단 |
| 배포 레코드는 없지만 Vercel 커밋 상태 존재 | 진행 중이거나 빌드가 실패한 경로와 구분해 조사 |
| 충분히 기다려도 배포와 상태가 모두 없음 | 배포 미생성으로 보고 훅 복구 |

## 훅 복구는 미생성에만 적용

훅 호출은 빌드 오류의 해결책이 아니다. 실행이 시작되지 않은 경우의 복구 수단으로 한정했다.

## READY 이후에 보이는 배포 레코드

배포 30건을 살펴보니 기록된 소요 시간은 보통 수 초, 긴 경우 85초였다. 특히 감시에 쓰는 GitHub 배포 레코드는 Vercel이 READY가 된 뒤에 나타났다. 이벤트가 전달되는 시간만 기준으로 잡으면 정상적으로 빌드 중인 실행도 미생성으로 오해할 수 있다. 대기 시간을 3분에서 5분으로 늘린 이유다.

## 내부 원인과 별개로 복구 경로 확보

수동 복구와 감시 경로를 만든 뒤 후속 작업에서 정상 동작을 확인했다. 이 사례는 모든 배포 장애의 원인을 자동으로 알아낸 이야기가 아니다. 외부 연동이 아무 실행도 남기지 않았을 때 발견하고 다시 시작할 수 있게 만든 사례다.
