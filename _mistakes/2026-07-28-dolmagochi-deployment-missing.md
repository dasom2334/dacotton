*이 글의 표기일은 7월 28일이며, 아래 실행 시각은 한국 시각으로 7월 29일 새벽이다.*

## 배포 기록이 0건이었다

7월 29일 01:56 침실 장면 PR #56을 main에 머지했다(`49ed47f`). 라이브는 그대로 7월 24일 01:47 커밋(`b60d6f9`)이었다. 그 사이 다른 머지는 없었으니, 배포되지 않은 것은 이 PR 하나다. 돌마고치는 main에 머지하면 Vercel이 GitHub 이벤트를 받아 프로덕션 빌드를 만드는 구조다. 그런데 새 커밋의 Vercel 배포 기록은 실패도 취소도 아니고 아예 없었다.

## 확인한 것과 끝내 모르는 것

확인한 것은 다음과 같다.

- GitHub은 push 이벤트를 보냈다. 같은 이벤트로 CI가 3초 뒤 돌았다.
- Vercel은 일시정지 상태가 아니었고, 프로덕션 브랜치는 main, 빌드 생략 조건은 없었으며, 계정과 저장소 접근도 정상이었다.

이 결과로 GitHub 이벤트 이후 배포 생성까지의 연결을 의심했다. 다만 Vercel 내부에서 어떤 일이 있었는지까지 확인한 것은 아니다.

빌드가 실패했다면 커밋에 실패 표시가 붙는다. 시작하지 않은 빌드는 아무것도 남기지 않는다. 그래서 화면이 안 바뀐다는 걸 사람이 눈치챌 때까지 아무 신호가 없었다. 실패 여부만 보는 감시로는 잡을 수 없는 유형이었다.

## 감시: 이 커밋의 배포가 생겼는가

main에 머지될 때마다 도는 GitHub Actions 작업을 붙였다. Vercel이 배포를 끝내면 GitHub Deployments에 Production 기록이 남는데(Deploy Hook으로 만든 배포도 남는 것을 확인했다), 감시는 머지한 커밋으로 이 기록이 생기는지 15초 간격으로 최대 20번, 5분 동안 확인한다. 권한은 배포 기록 읽기만 쓰고, 연달아 머지하면 앞선 감시를 취소하고 마지막 커밋만 본다.

## 대기 5분의 근거

처음에는 3분을 기다리게 했다가 실측 후 5분으로 늘렸다. 확인한 4건에서 GitHub의 배포 기록은 배포가 **완료(READY)된 1초 뒤에** 생겼다. 그래서 이 감시가 재는 것은 배포 완료까지의 시간이다.

| 구간 | 실측 |
| --- | --- |
| 커밋 → Vercel 배포 생성 | 3~6초, 느린 경우 85초 |
| 빌드 | 17~25초 |
| 합계(감시가 기다리는 시간) | 보통 약 30초, 관측한 네 건 중 최대 1분 43초 |

3분은 관측한 최대값의 약 1.75배였다. 공개 저장소라 러너 시간 비용이 없어 5분으로 늘렸다. 생성까지만 보고 대기 시간을 정하면, 정상적으로 빌드 중인 배포도 미생성으로 오해하게 된다.

## 구분: 빌드 실패인가, 미생성인가

5분을 기다려도 배포 기록이 없을 때는 원인을 한 번 더 가른다. Vercel은 빌드가 끝나면 커밋에 `Vercel` 상태를 남긴다(프로덕션 커밋 3건에서 확인). 유실된 커밋에는 이 상태가 없었다.

| 5분 뒤 관측 | 판단 | 처리 |
| --- | --- | --- |
| Production 배포 기록 있음 | 정상 | 통과 |
| 기록 없음, `Vercel` 상태 있음 | 빌드 실패 | 훅을 부르지 않고 실패로 알린다. 같은 커밋을 다시 빌드해도 또 실패한다 |
| 기록도 상태도 없음 | 배포 미생성 | Deploy Hook을 호출하고 다시 5분 동안 배포 기록을 확인한다 |

훅으로 복구해도 경고와 작업 요약을 남겨, 같은 일이 반복되면 Vercel에 문의할 근거로 삼게 했다.

## 결과

7월 29일 밀린 배포는 Deploy Hook으로 복구했다. 감시 작업은 7월 29일부터 9월 3일까지 16번 실행됐고, 10번은 성공으로 끝났으며 6번은 연달아 머지되면서 앞선 실행이 취소됐다. 이 기간에 감시가 훅으로 복구한 사례가 있었는지는 실행 로그를 열어 확인하지 않았다.

## 검증 범위

배포 미생성을 일부러 일으켜 훅 복구 분기를 재현하지는 않았다. 배포 기록 존재, READY 상태, 사용자가 받는 버전은 서로 다른 신호이며, 이 감시는 앞의 두 가지만 확인한다.
