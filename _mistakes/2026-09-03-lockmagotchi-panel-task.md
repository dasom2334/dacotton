## 새로 켜면 되는데 평소처럼 쓰면 안 됐다

9월 3일 자체 기기 제어 패널을 시험하면서 실행 순서에 따라 결과가 달라졌다. 앱을 강제 종료하고 잠금화면에서 들어가면 정상인데, 일반 앱을 한 번 열고 홈으로 나간 다음 잠그면 패널 카드가 비었다. 사용자가 자연스럽게 할 법한 순서가 오히려 실패 조건이었다.

이 차이가 원인을 좁히는 단서였다. 장면 렌더링이나 저장값이 항상 잘못됐다면 강제 종료 여부만으로 화면이 살아나는 것을 설명하기 어려웠다. 앱의 기존 실행 상태를 포함해 살펴봐야 했다.

## 패널은 실행됐지만 들어간 태스크가 달랐다

Android는 함께 움직이는 화면을 태스크라는 실행 묶음으로 관리한다. 잠금화면을 그리는 SystemUI는 패널용 표시 영역인 TaskView를 준비했다.

ActivityTaskManager 로그에는 패널이 MainActivity를 루트로 둔 앱 태스크에 들어간 것으로 나왔다. SystemUI의 패널 카드는 별도 TaskView에 화면을 담으려는데, Activity가 이미 있던 앱 태스크로 합류한 것이다. 화면을 띄우라는 호출이 실행됐다고 올바른 자리에 표시된 것은 아니었다.

앞서 Flutter 셸을 쓸 때는 MainActivity에 비어 있는 taskAffinity가 붙어 있었다. 패널이 합류할 기존 태스크가 없어 문제가 가려졌다. 네이티브 MainActivity로 전환하면서 이 조건이 달라져 재현되기 시작했다. Flutter가 있어야 동작하는 기능이 아니라, 템플릿 속성이 우연히 실행 경로를 바꿨던 사례다.

## 패널의 실행 단위를 독립시켰다

패널 화면인 PanelActivity에 `android:taskAffinity=""`를 지정해 일반 앱의 기존 실행 묶음에 합류하지 않도록 했다. 이후 로그에서는 패널이 독립적인 multi-window 태스크로 생성됐고, 같은 잠금 상태에서 자체 화면과 버튼이 나타났다. 검증은 Pixel 7 프로필 API 36 에뮬레이터에서 수행했다.

이 속성을 모든 Activity에 일괄 적용하는 규칙으로 일반화하지는 않는다. 핵심은 다른 UI 안에 들어갈 화면의 태스크가 기존 앱 화면과 어떻게 결합하는지 확인하는 것이다. 이 사례에서는 패널이 일반 앱 태스크에 합류하지 않아야 했다.

## 다음 재현에는 사용 순서를 포함한다

잠금 패널은 앱을 처음 설치한 직후에만 쓰는 기능이 아니다. 앱을 켰다 닫고, 배경에 남겨 두고, 잠갔다가 다시 들어갈 수 있다. 이후 검증에는 이 실행 순서를 포함해야 한다. 강제 종료 뒤 한 번의 성공만으로는 태스크 수명 문제를 놓칠 수 있다.
