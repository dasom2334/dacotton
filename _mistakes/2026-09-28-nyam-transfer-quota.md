## 무료 베타가 감수한 것은 콜드스타트만이 아니었다

냠은 최대 200명 정도의 커뮤니티 베타에서 쓰임과 수익 가능성을 확인하려고 무료 인프라를 선택했다. 이용자가 많지 않으면 DB 사용량도 작을 것처럼 보이지만, 운영자가 수행하는 수집·적재·검증도 DB를 사용한다. 당시 예상은 방문당 요청과 전송량에 기대고 있었다. 9월 13일에는 예상 방문 규모가 작다는 이유로 DB 전송량 경보를 미뤘지만, 브랜드를 늘리는 동안의 백업·재처리·검증은 그 예상과 따로 살펴야 했다.

9월 28일 배포는 마이그레이션 단계에서 할당량 초과로 실패했다. 관리 화면에는 월 네트워크 전송량 소진과 5.96GB가 표시됐고, 간단한 SELECT 1도 거절됐다. 잠든 DB가 깨어나기를 기다리는 상황과 달리 같은 배포를 반복한다고 해결되지 않았다.

## 의심한 경로와 입증한 원인을 나누기

당시 반복한 전체 백업·전체 원재료 재처리·전체 API 검증이 전송을 늘렸을 가능성이 있었다. 로컬에는 9월 27일 백업 13개가 있었지만 압축 파일 크기를 합해 실제 DB 전송량이라고 계산할 수는 없었다. 작업별 전송 계측이 없어 각 원인이 얼마를 썼는지는 분리하지 못했다.

따라서 ‘백업 한 가지가 전부 소진했다’고 결론 내리지 않았다. 확인한 것은 실제 한도 차단과 반복 전체 작업의 존재였다. 추가 전체 조회와 백업을 멈추고, 계정 API로 당시 소비 주기의 종료 시각을 확인했다. 그 시각은 복구 예정의 근거이지 실제 복구 성공을 미리 보장하는 관측은 아니었다.

## 검증을 줄이기보다 읽는 범위를 줄이기

후속 구현에서는 로컬에서 준비한 제품·관측 묶음을 운영에 보내고, 운영 검증도 그 묶음의 키만 읽게 했다. 사전이 바뀌면 전체 이력을 다시 계산하는 대신 영향을 받은 표기를 가진 이력만 재계산했다. 10월 11일에는 변경분 적재와 사전 동기화의 실제 적용 결과가 남았다.

대신 묶음의 사전 버전과 대상 상태가 맞는지 확인하고, 같은 묶음을 두 번 적용하지 않는 원장을 관리해야 했다. 운영에서 언제든 전체 재계산하면 된다는 단순함을 포기하고, 작은 변경의 영향을 좁히는 비용을 받아들인 것이다.

## 사용자 트래픽과 관리 작업을 따로 예산에 넣기

이번 문제는 무료 티어 자체가 잘못된 선택이었다는 결론보다, 사용자 요청 수만으로 운영 비용을 예상할 수 없다는 경험이다. 이후에도 제조사 HTTP 다운로드, DB 전송, 모델 호출 비용을 같은 숫자로 섞지 않아야 한다.

후속 변경이 실제로 월 전송량을 얼마나 줄였는지는 여기서 입증하지 않았다. 줄인 것은 반복 처리 범위이며, 다음에는 작업별 계측으로 비용과 검증 범위를 함께 확인해야 한다.
