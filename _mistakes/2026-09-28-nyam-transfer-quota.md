## 배포가 마이그레이션 단계에서 멈췄다

9월 28일 냠 배포가 DB 마이그레이션 단계에서 할당량 초과로 실패했다. Neon 관리 화면에는 9월 11일부터 쓴 월 네트워크 전송량이 5.96GB로, 무료 한도 5GB를 넘었다고 나왔다. 컴퓨트가 차단돼 `SELECT 1`도 거절됐다. 잠든 DB가 깨어나기를 기다리는 콜드스타트와 달리, 같은 배포를 다시 돌려도 풀리지 않았다.

## 무엇이 전송량을 썼나

9월 13일 무료 인프라를 고를 때는 사용자 방문으로 전송량을 예상했다. 목록을 두 번 여는 방문 하나에 약 1.2MB, 무료 5GB면 월 약 4,100방문이었다. 운영자가 돌리는 작업은 이 계산에 없었다.

브랜드를 늘리던 같은 기간에 운영 DB 전체를 읽는 작업 세 가지를 반복했다.

| 반복한 작업 | 읽는 범위 |
| --- | --- |
| 운영 DB 전체 백업 | 모든 테이블 (9월 27일 하루에만 13개) |
| 원재료 전체 재처리 | 브랜드를 하나 더해도 모든 제품의 원문과 관측 |
| 공개 API 전체 검증 | 모든 공개 제품 |

Neon 화면은 작업별 전송량을 보여 주지 않았고, 작업마다 따로 재지도 않았다. 9월 27일 백업 13개의 압축 파일 합계는 약 104MB였지만, 압축 파일 크기는 DB가 내보낸 바이트와 다르므로 전송량으로 환산하지 않았다. 그래서 원인은 '운영에서 전체를 읽는 반복 작업'까지만 좁혔고, 셋 중 무엇이 얼마나 썼는지는 모른다.

당장 운영 전체 조회와 전체 백업을 멈췄다. 같은 날 원재료 재처리에 브랜드 지정 옵션을 넣어, 고른 브랜드의 원문만 읽고 다른 브랜드의 원료 횟수는 DB 집계로 보존하게 했다(`7bf1107`). 다만 사전 변경을 반영하는 공개 계산은 이때도 전체 관측 입력을 읽었다.

## 운영은 묶음의 키만 읽는다

10월 11일부터는 로컬에서 검증한 제품·이력·원료·성분·관측을 변경분 묶음으로 만들어 운영에 보낸다. 적용 후 확인도 그 묶음에 든 키(브랜드 식별자와 제품 식별 문자열)로만 다시 읽는다. 이날 일곱 브랜드 51개 제품 묶음을 2분 18초에 적용했고, 키별 재조회에서 불일치는 0건이었다.

## 사전 변경은 영향받은 이력만 다시 계산한다

원료 사전이 바뀌면 예전에는 전체 이력을 다시 계산했다. 이번에는 바뀐 용어가 등장하는 이력만 찾아 계산한다. 10월 11일 운영 점검에서 별칭 286개가 부족해 먼저 동기화했고, 바뀐 용어 42개가 등장하는 이력 1,679개만 다시 계산했다. 당시 전체 이력은 5,888개였다. 다시 계획을 뽑았을 때 추가로 필요한 별칭·용어·영향 이력은 모두 0이었다.

## 같은 묶음을 두 번 적용하지 않는 원장

변경분만 보내면 "운영에서 전체를 다시 계산해 맞추면 된다"는 안전망이 사라진다. 그래서 묶음 적용 자체를 안전하게 만들어야 했다.

| 장치 | 막는 것 |
| --- | --- |
| 적용 전 계획을 보여 주고, 쓰기에는 그 계획의 해시를 요구 | 준비한 묶음과 다른 인자로 적용하는 것 |
| 카탈로그 잠금 안에서 사전 해시와 제품·용어 상태를 다시 검사 | 계획 이후 운영 상태가 바뀐 채 적용하는 것 |
| 제품 변경과 원장 기록을 한 트랜잭션으로 처리 | 적용 도중 실패해 일부만 남는 것 |
| 원장에 묶음 식별자와 결과를 남기고, 재제출 시 `already_applied` 반환 | 같은 묶음이 두 번 들어가 제품·이력이 중복되는 것 |

전체 재계산보다 영향 범위를 찾는 코드와 원장 관리가 복잡해졌다. 대신 작은 변경 하나에 운영 전체를 읽지 않게 됐다. 자세한 적용 과정은 [변경분 반영 로그](/log/2026/10/11/nyam-catalog-release/)에 있다.

## 검증 범위

후속 변경으로 월 전송량이 실제로 얼마나 줄었는지는 재지 않았다. 줄인 것은 운영에서 읽는 범위다. 재적용 검사는 완료된 묶음을 다시 보내는 경우만 확인했고, 커밋 직후 연결이 끊기는 장애는 시험하지 않았다.
