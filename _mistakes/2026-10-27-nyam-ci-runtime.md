## 테스트 실패도 아니었다

냠은 코드 변경을 GitHub Actions에서 검사하고 같은 서비스로 배포한다. 10월 26일 PR 검사를 다시 실행했지만 약 3초 만에 끝났다. 결제 실패 또는 지출 한도 조정이 필요하다는 메시지였고, 테스트는 시작하지도 못했다. main의 배포도 같은 실행 환경에 의존해 머지를 보류했다.

사용 시간을 작업별로 [분 단위 올림](https://docs.github.com/en/billing/reference/actions-runner-pricing)해 합산한 내부 집계는 2,029분이었다. GitHub 제공 서버 2,028분과 자체 서버 1분을 포함한 실행 시간 집계다. 이 내역에서는 운영 서버에 들어가지 않는 코드 변경도 검사와 빌드를 반복하고 있었다.

먼저 실행할 필요가 없는 작업부터 줄였다. PR 검사는 유지하되 실행 도구·크롤러만 바뀐 main에서는 중복 검사와 배포를 생략했다. 서버나 웹 등 운영에 영향을 주는 변경에는 계속 실행하고, 웹·이미지 빌드 여부를 판별하지 못하면 둘 다 실행하도록 했다. PR에 새 커밋이 올라오면 [이전 실행을 취소](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)하고, 중복된 빌드도 덜었다.

## 가짜 모델도 진짜 프로그램이었다

실행 횟수를 줄인 다음에는 한 번의 검사 안에서 무엇을 기다리는지 봐야 했다. 수집 작업에 쓰는 AI 실행 도구의 테스트는 가짜 모델을 별도 프로그램으로 띄웠다. 테스트가 끝날 때까지 상태를 반복 확인하고 기다리는 과정은 실제였다.

검사하려던 것은 잘못된 출력을 받았을 때 재시도하는지 같은 판단이었다. 그 판단을 확인할 때마다 별도 프로그램의 실행과 종료를 기다릴 필요가 있을까. 나는 이 부분을 작은 판단 단위의 테스트로 나누고 외부 실행은 대역으로 바꾸는 기준을 택했다. 대역은 실제 프로그램 대신 정해진 성공·실패 결과를 돌려준다.

로컬 검수 명령도 입력 확인, 기대값 준비, DB 저장, 결과 비교, 보고를 분리했다. 이 구분이 있어야 입력 검사나 비교 로직을 확인할 때 매번 실제 DB 저장까지 실행하지 않을 수 있었다. 저장 동작 자체의 검사는 서버 쪽에서 맡도록 했다. 변경 당시에는 이전 CLI 검사 16개를 새 코드에서 실제로 실행했고, 같은 원문을 이전·새 CLI에 넣어 보고서도 비교했다. DB 경로와 스크립트 자체의 코드 해시를 제외하면 같았다. 이는 전환 시 한 번 확인한 결과이고, 바뀐 유닛 테스트가 계속 실제 적재를 검사한다는 뜻은 아니다.

## 빨라졌지만 같은 검사는 아니었다

대역으로 바꾸면 실제 실행에서만 생기는 문제는 덜 볼 수 있다. OS가 파일 쓰기를 차단하는지 직접 실행하던 검사는 차단 설정을 올바른 인자로 넘기는지 확인하는 검사로 바뀌었다. 설정 전달이 맞다는 결과와 OS가 실제로 막았다는 결과는 같지 않다.

마지막에 남은 프로세스 검사도 대역으로 바꿨다. 집합의 순서가 달라져도 결과가 같은지 확인할 때, Python을 다른 해시 시드로 새로 실행하는 대신 입력 순서를 바꿔 검사했다. 판단 로직을 빠르게 확인하는 쪽을 택한 만큼 실제 인터프리터의 동작까지 검증한다고 볼 수는 없었다.

서버 테스트에는 분석값과 제품 이력의 실제 저장 검사가 남았다. 반면 대역으로 바꾼 검사는 OS가 실제로 파일 쓰기를 차단하는지, 두 프로세스가 동시에 접근할 때 잠금이 작동하는지까지 확인하지 않는다. 최종 변경 뒤에는 주간 예약 실행이 실제 갱신 프로그램까지 이어지는 흐름도 실행해 보지 않았다. 파일 권한·프로세스 종료·잠금·예약 실행의 연결 문제는 대역 검사의 통과만으로 판단할 수 없었다.

## 줄어든 시간을 따로 셌다

당시 실행 도구 검사 묶음은 67~89초에서 25초, 후속 수정 뒤 22초로 줄었다고 보고됐다. 별도의 로컬 전체 실행 출력에는 627개 검사 중 6개 건너뜀·실패 없음, 32.325초가 남았다.

회고 때는 실행 도구의 한 모듈 34개만 수정 전후 각각 세 번 실행했다. 여섯 실행 모두 성공했고, 실행 시간 중앙값은 약 11.19초에서 0.39초로 줄었다. 이는 당시 전체 검사 묶음과 다른 범위의 재현이다. 월간 사용량은 실행 횟수에도 달려 있으므로 이 결과는 테스트 실행 시간의 개선으로 남겼다.

이번에는 반복 자체를 없앤 부분과 검사 방법을 바꾼 부분이 함께 있었다. PR의 중복 실행을 취소하는 것은 같은 일을 덜 하는 변경이다. 실제 프로세스를 대역으로 바꾸는 것은 무엇을 검증할지 바꾸는 선택이다. 둘을 나눠야 짧아진 시간과 남은 검사 범위를 함께 설명할 수 있었다.
