## 새 버전만 멈춘 줄 알았다

냠은 사료의 원료와 영양성분을 보여 주는 서비스다. 영어 화면을 추가하는 배포가 점검 단계에서 실패했지만, 사용자 요청은 여전히 이전 서버가 받고 있었다. 서버 상태 확인과 제품 목록도 정상 응답인 HTTP 200을 돌려줬다.

상세 화면에서 사용하는 DB 필드 이름은 달랐다. 배포에는 `country`를 `language`로 바꾸는 작업이 포함돼 있었고, 이전 코드는 아직 `country`를 읽었다. 상세 요청을 따로 실행한 결과 목록은 200, 상세는 서버 오류인 500이었다. 정상 목록만으로는 사용자에게 제공하는 기능 전체가 살아 있다고 판단할 수 없었다.

## 요청을 넘기기 전에 바뀐 것

배포 순서는 DB 구조 변경, 사용자 요청을 받지 않는 새 서버 실행, 동작 점검, 새 서버로 요청 전환이었다. 새 버전의 점검이 실패하면 요청을 넘기지 않는 장치는 있었다. 그러나 그보다 앞서 실행한 DB 변경까지 취소하는 장치는 아니었다.

이전 서버와 새 서버는 같은 DB를 사용했다. 이전 서버를 계속 실행해도 그 서버가 기대하는 필드 이름까지 보존되지는 않았다. 점검 실패가 막은 것은 새 서버로의 전환이었고, 이전 서버가 읽는 데이터 구조는 이미 바뀌어 있었다.

새 서버가 실패한 이유도 따로 있었다. 브랜드 영어 이름이 들어 있는 `brands.json`이 서버 실행 파일을 묶은 Docker 이미지에 빠졌다. 저장소에서는 보이던 파일이지만 Dockerfile은 서버 디렉터리만 복사했고, 코드는 그 바깥의 `/brands.json`을 읽었다. 새 코드는 바뀐 DB에 맞았으나 필요한 파일 없이 실행할 수 없었다.

## 파일을 넣고 상세를 다시 열었다

복구에서는 DB 필드 변경을 되돌리는 대신, 누락 파일을 갖춘 새 버전을 배포했다. Dockerfile에 `COPY brands.json /brands.json`을 추가한 수정이었다. 이후 테스트와 배포가 성공했고, 앞서 500이었던 상세 요청이 200으로 돌아왔다. 응답의 번역 데이터에서도 `ko` 키를 확인했다.

복구 확인은 처음부터 성공하던 상태 확인이나 목록 요청에만 머물지 않았다. 이번에 이름이 바뀐 필드를 실제로 읽는 상세 요청이 통과해야, 실패했던 기능이 돌아왔다고 할 수 있었다.

## 배포가 중간에 멈춘 상태도 남는다

이번 복구는 누락 파일을 넣은 새 서버로 완료했다. DB 변경을 여러 단계로 나누는 구조까지 구현한 것은 아니다.

다음에는 새 필드를 먼저 추가하고 데이터를 옮긴 뒤 서버를 전환하며, 이전 서버가 사라진 후 옛 필드를 제거하는 방식을 검토할 수 있다. 전환 기간에 두 필드의 값을 맞추는 일이 늘지만, 새 서버의 점검이 실패해도 이전 서버가 사용할 구조를 남길 수 있다.

이 배포에는 새 서버를 점검한 뒤 요청을 넘기는 조건이 있었다. 빠져 있던 것은 그 조건에 도달하기 전에 바뀐 DB와 이전 서버의 관계였다. 새 버전으로 전환하지 않았다는 결과만으로 운영이 그대로라고 볼 수 없었다.
